Self-hosting

Yes, you can run it. hedgehog-pr-bot is built for one GitHub account — yours, not as a multi-tenant service. You bring your own GitHub App, a host with a public HTTPS endpoint, and a model API key. Everything else is one Docker Compose service.

Heads-up on naming: GitHub App slugs are globally unique and hedgehog-pr-bot is taken, so name your App anything you like and set BOT_LOGIN to its bot account slug (the part before [bot]). Without it the bot cannot recognize its own threads, 👀, and reviews, so thread follow-up and unblocking dismissal degrade.

What you need

  • A GitHub account (personal or org) allowed to create GitHub Apps.
  • A Docker host with a public HTTPS endpoint — a small VPS with Caddy or nginx in front, or a tunnel such as Cloudflare Tunnel.
  • An API key for at least one model provider Pi supports (Z.AI, Anthropic, OpenAI, …).
  • Node.js 24+ only if you want to run the test suite or typecheck locally.

1. Create your GitHub App

  1. Go to Settings → Developer settings → GitHub Apps → New GitHub App. Pick any name (this becomes the bot account, e.g. my-reviewer[bot]) and note the slug for BOT_LOGIN.
  2. Set the webhook URL to https://your-host/github/webhook and the webhook secret to a fresh openssl rand -hex 32 value — the same value you will put in GITHUB_WEBHOOK_SECRET.
  3. Under Permissions & events: Contents read; Issues read & write; Pull requests read & write; Checks write. Subscribe to the Pull request and Issue comment events.
  4. Generate a private key at the bottom of the App page, then base64 it: 
    base64 < app.private-key.pem | tr -d '\n'
    Note the Client ID (Iv1.…) shown on the same page.
  5. Install the App on your account — all repositories, or the subset to review.

2. Deploy the server

  1. Clone (or fork) the repository onto your host.
  2. Copy .env.example to .env and fill it in: 
    APP_CLIENT_ID=Iv1.xxxx
APP_PRIVATE_KEY_BASE64=base64-pem
GITHUB_WEBHOOK_SECRET=your-webhook-secret
ZAI_API_KEY=your-model-key

BOT_LOGIN=my-reviewer
PR_AUTHOR=your-username
PI_MODELS=zai/glm-5.3:high
  3. Start it and confirm health: 
    docker compose up -d --build
curl -s https://your-host/healthz   # {"ok":true,...}

The container runs as an unprivileged user, read-only, with all Linux capabilities dropped, and binds 127.0.0.1:3000 on the host by default for your TLS proxy. Set BIND_ADDRESS=0.0.0.0 only if your firewall and proxy require it.

3. Optional: hourly recovery scan

Webhook deliveries can be missed while the server is down. The included .github/workflows/review.yml reconciles open PRs hourly using a short-lived App token minted inside Actions. On a fork:

  1. Enable Actions on your fork.
  2. Add repository secrets APP_PRIVATE_KEY and ZAI_API_KEY, and variables APP_CLIENT_ID and (optionally) PI_MODELS.
  3. Edit the workflow’s token step to target your owner (or remove the owner: line so it defaults to the repository owner) and set PR_AUTHOR/BOT_LOGIN in the run step’s environment to match your server.

Keep PI_MODELS identical between server and scan — the review fingerprint is derived from it, and a mismatch means everything gets re-reviewed.

Day-to-day

docker compose ps
docker compose logs -f hedgehog-pr-bot
docker compose up -d --build   # after pulling changes
  • Queue is in memory; restarts lose pending work and the hourly scan recovers it.
  • Reviews run sequentially so you don’t hammer your model plan; a new push while a review runs simply queues behind it.
  • Big diffs are capped at MAX_DIFF_CHARS (4M by default) — split huge PRs for better feedback.

Costs and limits

  • Model usage is yours: one Pi pass per configured model per reviewed head. The hourly scan caps itself at MAX_REVIEWS_PER_RUN (5).
  • Single-author by design: only PR_AUTHOR’s PRs are reviewed.
  • Security posture: webhook signatures verified before parsing; tokens, the App key, and the webhook secret removed from the model’s environment; Pi runs with tools, extensions, skills, and sessions disabled, and PR text is treated as untrusted data — never instructions.
